# pull request の規則

PadServer の PR を, 誰がどう作って, どう merge するかを決めたものです.
「所有者」と「本体」の意味は, [roadmap.md](roadmap.md) の冒頭にあります.
「実装者」は Issue を実装するワーカー, 「reviewer」はレビューをするワーカーを指します. どちらも Codex (gpt-6-luna) で, 本体が Issue ごとに立てます.

## 1. 単位

- 1つの Issue に, 1つの PR を作ります. 1つの PR は, 1つの Issue だけを閉じます.
- Issue に書いていない変更を混ぜません. 途中で要ると分かった変更は, 新しい Issue にします.
- コードを変えない Issue (通しの確認など) は, PR を作りません. 結果を Issue のコメントに書いて閉じます.

## 2. branch と worktree

- branch は main から切ります. 名前は `<type>/<Issue の番号>-<短い説明>` です. 例は `feat/56-authorize-admin` です.
- `<type>` は, commit と同じ6つ (feat, fix, improve, refactor, add, enhance) から選びます.
- worktree は, Issue ごとに1つ作ります. 同じファイルを触る Issue は, 同時に走らせません.
- merge された後, 本体が worktree と手元の branch を消します.

## 3. 流れ

| 順 | 誰が | すること |
| --- | --- | --- |
| 1 | 本体 | Issue を指示文にする |
| 2 | 実装者 | worktree で実装する. commit はしない |
| 3 | reviewer | 1回レビューする. 終わりの確認のコマンドを, 自分で実行し直す |
| 4 | 本体 | reviewer の指摘を直す. 再レビューはしない. 画面のある実装と, 動かして見せられる実装は, このときにスクリーンショットを撮る |
| 5 | 本体 | 4章の検査を通して, commit, push, PR の作成, スクリーンショットの投稿までを続けて行う. 所有者の確認は待たない |
| 6 | 所有者か merge 係 | merge する |

- 実装者と reviewer は, commit も push もしません. commit, push, PR の作成は, 本体だけが行います.
- 成果物が動くことは, reviewer が確かめます. 本体は, ビルドや動作を自分で確かめ直しません. 本体が行うのは, 4章の検査です.
- 文書だけを変える PR では, reviewer を回しません. 本体が4章の検査で確かめます.

## 4. push の前に通す検査

| 検査 | 中身 |
| --- | --- |
| lint, secret, 綴り | `pre-commit run --all-files` が通る |
| ビルドと試験 | `swift test` が通る. アプリを触ったときは, `xcodebuild build` も通る |
| README | PR が `README.md` を変えていない (README は #193 で最後に書く) |
| 個人的な情報 | 端末の ID, IP, tailnet の名前, Team ID, メールアドレス, 個人の名前, token が, 差分にもスクリーンショットにも無い |

1つでも落ちたら, push しません.
pre-commit が入るまで (M0-7 が済むまで) は, その Issue に関わる検査を手で実行します.

### 4.1 CI と同じ script を手元で走らせる

CI の build と試験の手順は, `scripts/ci/` の script (`core.sh`, `cli.sh`, `relay.sh`, `app.sh`, `unused-code.sh`) にあります. CI の workflow と pre-push の hook は, 同じ script を呼びます.

- 手動で走らせるには, `scripts/ci/<名前>.sh` を直接呼ぶか, `pre-commit run --hook-stage pre-push --all-files` を実行します. どちらも引数は要らず, repo のどこからでも呼べます.
- push の前に自動で走らせるには, `pre-commit install --hook-type pre-push` を1回実行します. 入れると, `git push` の前に 10 分ほどかかります.
- pre-push の hook は強制ではありません. 飛ばしたいときは, `git push --no-verify` を使わずに, CI に任せます.
- pre-push の hook は, `pre-commit run --all-files` (commit の stage) では走りません.

## 5. commit

- メッセージは `<type>: <10語ほどの説明>` の1行で, 英語で書きます.
- `Co-Authored-By` を付けません. `--amend` を使いません.
- 1つの commit には, 1つの論理的な変更だけを入れます.

## 6. タイトルと本文

タイトルは, Issue と同じにします. 例は `[M2-19] use case: 管理の認可` です.

本文は日本語で, 次の形にします.

```markdown
Closes #56

## 実装内容

何を作ったかと, なぜそうしたかを, 3行から6行で書く.

## 変更点

| 変更した所 | 何を変えたか | 何のための変更か |
| --- | --- | --- |
| `path/to/File.swift` | 変えた中身 | この変更で, 何ができるようになるか |

## API の変更

API を足したときと, 変えたときだけ書く.

| 対象 | 区分 | 何を変えたか | 何のための変更か |
| --- | --- | --- | --- |
| `POST /v1/projects/{name}/deploy` | 新規 | 要求と応答の形 | この変更で, 何ができるようになるか |

## 画面と動作

画面のある実装と, 動かして見せられる実装のときだけ書く.
スクリーンショットは, この PR のコメントに載せた.

## 検証

実行したコマンドと, その出力をそのまま貼る.

## レビューの指摘

| 重さ | 場所 | 指摘 | 対応 |
| --- | --- | --- | --- |
| blocking | `path:line` | 指摘の中身 | 未対応 |
```

### 6.1 変更の目的を書く

- 変更は1つずつ, 「何を変えたか」と「何のための変更か」を対にして書きます. ファイルの名前を並べるだけにしません.
- 目的を書けない変更は, その PR に入れません.

### 6.2 API の変更を書く

- ここでの API は, 外から見える約束ごとを指します. 管理 API の endpoint, 通信の型, relay の取り決め, `padctl` のコマンドと引数, `padserver.toml` の形です.
- 足したものは「新規」, 変えたものは「変更」と書きます. 変更では, 前と後で何が変わったかを書きます.
- 1つずつ, 何のための変更かを書きます.

### 6.3 スクリーンショットを載せる

画面のある実装と, 動かして見せられる実装は, 動いている様子をスクリーンショットに撮って, PR のコメントに載せます.

| 対象 | 撮るもの |
| --- | --- |
| アプリの画面 | iOS Simulator の画面. 実機でしか確かめられないものは, 実機の画面 |
| ブラウザで開くページ | 配信した静的サイトや, container のサービスを開いた画面 |
| `padctl` | コマンドを実行した端末の画面 |

- 画面を変えたときは, 変更前の画面を先に, 変更後の画面を後に並べます.
- 新しく足した画面は, 変更前の画面が無いことを書きます.
- 撮った画像は, 載せる前に目で確かめます. public に見えるので, token, IP, 端末の名前, tailnet の名前が写っていないことも確かめます.

### 6.4 署名を付けない

- PR の本文とコメントに, 「Generated with Claude Code」などの署名を付けません.
- commit に, `Co-Authored-By` を付けません.

### 6.5 README は最後に書く

PR では, `README.md` を変えません. README は, 開発の最後に, 1回だけ書きます (Issue #193).

- 「何ができるか」は, PR の本文の「実装内容」に書きます.
- 動いた証跡は, PR の本文の「検証」に書きます. 画面のある実装と, 動かして見せられる実装は, 6.3 のとおりスクリーンショットを撮って, PR のコメントに載せます.
- 理由は, 全ての PR が README の末尾に足すと, 1件 merge するたびに, 他の全ての PR が衝突して, CI をやり直すためです (決定 85).

## 7. レビューの指摘

- reviewer の指摘は, 本体が選別せずに, 全件を本文に載せます.
- 指摘は, 所有者に聞かずに, 本体が直してから PR を出します. 直した指摘は, 表の「対応」の欄に commit の番号を書きます.
- 直さなかった指摘は, 理由を「対応」の欄に書いて残します. Issue の範囲の外にある指摘は, 新しい Issue にします.
- CI が落ちたら, 本体が原因を調べて直します. 落ちたまま, merge を頼みません.

## 8. merge

- merge するのは, 所有者か, 所有者が指名した merge 係です. merge 係の手順は, [AGENTS.md](../AGENTS.md) の2章にあります.
- 方法は merge commit にします. GitHub の画面では「Create a merge commit」です.
- PR の commit は, 番号を変えずに main に入ります. PR ごとに, merge 用の commit が1つできます.
- merge 用の commit のメッセージは, GitHub が付けたままにします. 5章の形には合わせません.
- GitHub の設定で, merge の方法を merge commit だけにして, merge 後の branch を自動で消すようにします. main の保護 (M0-17) と一緒に設定します.
- 他の PR が先に入って衝突したら, 本体は自分で直さずに, 所有者に知らせます. 直し方は, その場で決めます.
