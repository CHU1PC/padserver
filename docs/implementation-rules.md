# 実装の規則

PadServer のコードを書くときに守ることです. 実装者にも, 本体にも当てはまります.
PR の作り方は [pull-requests.md](pull-requests.md) に, 層の分け方は [roadmap.md](roadmap.md) の 2.3 にあります.

## 1. 進め方

- Issue の「やること」と「触る場所」の外に, 手を出しません. ついでの整理や機能の追加をしません.
- 途中で, 他の場所の変更が要ると分かったら, 止めて報告します. 自分の判断で広げません.
- 本体が書いた型, port, 通信の型を変えません. 変えたいときは, 理由を添えて報告します.
- 試験を先に書いて, 落ちることを見てから実装します.
- 「動くはず」で終わりにしません. Issue の「終わりの確認」のコマンドを実際に実行して, 出力を報告に貼ります.
- 実装者は commit も push もしません. PR も作りません.

## 2. 層

- 依存の向きは, 外側から内側だけです. PadDomain は, 他の層も外部の framework も import しません.
- 外部の framework (Hummingbird など) を import できるのは, PadInfrastructure と PadGuest だけです.
- use case は, 保存や guest に直接触りません. port (protocol) を通します.
- App は組み立てと画面だけを持ちます. 判断を伴う処理を App に書きません.
- ファイルの名前と中身の責務を合わせます. 違うものを扱う関数を, 同じファイルに置きません.

## 3. 型

| 使わないもの | 代わりにすること |
| --- | --- |
| `Any`, `AnyObject`, `[String: Any]` | 中身に合った型を定義する |
| `!` での強制 unwrap, `try!`, `as!` | `guard let` と `throws` で, 失敗を呼び出し側に返す |
| `@unchecked Sendable`, `nonisolated(unsafe)` | 値型にするか, actor に持たせる |
| `// swiftlint:disable` | 規則に沿って書き直す |
| 3つ以上の要素を持つ tuple, キーが決まっている dictionary | struct を定義する |

- 値は struct で, 変わらないものは `let` で持ちます.
- 外から受け取る JSON は, `Codable` の型で受けて検証します.
- 上の表の例外は, 型では表せないことが分かっている場合だけです. そのときは, 理由をその行にコメントで書きます.

## 4. 設計

- class と actor は, 共有する状態を持つときだけ使います. 状態が無ければ, 関数か struct にします.
- どこからでも書き換えられる状態 (`static var`, `shared` の singleton) を作りません. 要るものは init で渡します.
- ネストを浅くします. `guard` で早く抜けます. 関数の中に関数を書きません.
- 呼び出しが1か所で, 中身が2行から3行の関数は作りません. 層の境界をまたぐものは例外です.
- 実装が1つしか無い protocol を作りません. port は例外です.
- 使っていないコードと import を残しません. 既にある処理を, 別の場所で書き直しません.

## 5. 値と secret

- 意味のある数値 (timeout, 上限, 件数) には名前を付けて, その値にした根拠をコメントに書きます.
- secret と token は Keychain に持ちます. ログ, エラーの文, 試験のコードに出しません.
- 個人的な情報 (端末の ID, IP, tailnet の名前, Team ID, メールアドレス, 個人の名前) を, コードにも試験にも書きません. 見本の値には `example.com` を使います.

## 6. エラーと並行処理

- エラーを握りつぶしません. `try?` で捨てたり, 空の `catch` を書いたりしません.
- 広く捕まえるときは, なぜ広く捕まえるのかをコメントに書きます.
- 独自のエラーの型は, 呼び出し側がその種類で分岐するときだけ定義します.
- 並行処理は, Swift の concurrency (`async` と `await`, actor, `TaskGroup`) で書きます. `DispatchQueue`, `Thread`, lock, semaphore を新しく書きません.
- QEMU を動かす専用の thread だけは例外です. PadGuest の中に閉じ込めます.
- 待つ処理には, 必ず timeout を付けます. 起動した `Task` は参照を持って, 取り消しに対応します.

## 7. 試験

- 試験は Swift Testing (`import Testing`) で書きます.
- use case と値の型には, 必ず試験を付けます.
- 外の世界の代わりには, PadTestSupport の in-memory の実装を使います. mock のライブラリは入れません.
- 時刻と ID は, port から受け取って固定します. 試験の中で, 実際の時刻や乱数に頼りません.
- 実際のネットワーク, Keychain, QEMU に触る試験は, 普通の試験と分けます.

## 8. コメントと名前

- ファイルの先頭に, 説明のコメントを書きません.
- コメントは, 消すとコードから読み取れなくなる情報だけを書きます. 1行に収めます.
- 型と関数の説明は, 1行の要約と, 引数, 戻り値, エラーだけにします.
- コメントは日本語で書けます. 名前, ログ, エラーの文は英語で書きます.

## 9. 依存と, Swift 以外のコード

- 外部の依存を, 勝手に足しません. 足したいときは, ライセンスを確かめたうえで, 所有者に聞きます.
- relay の TypeScript は, bun で管理します. `any` を使いません.
- shell の script は, `set -euo pipefail` で始めます. shellcheck と shfmt を通します.
